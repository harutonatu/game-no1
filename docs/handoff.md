## 4. 作業環境で分かったこと（事実）

- **作業環境の再起動**：この会話の間に何度か入れ替わった。担当（サブエージェント）と、裏で流していたテストは止まって結果が無くなる。対策：途中の成果はこまめにコミットして push する、絵などは 1 タスク 10 枚まで・1 枚ごとにファイルへ書く、テストの出力はファイルに書く（scratchpad も消えることがある）。
- **関門の時間**（クラウド 4 コア）：Chromium smoke 約 2〜3 分、full 約 8〜11 分、WebKit smoke 約 11〜15 分。1 本ずつ順に流す（同時に流すと WW10・BW31 など速さや時間の項目が落ちる）。
- **通信**：メトロポリタン美術館の API は使える。ウィキメディアは回数制限（429）。GitHub Pages（github.io）はこの環境から見られないので、公開の確認はユーザーの実機で行う。
- **絵の描き方**：楕円・四角・三角とふちどりの部品で描いて最後に文字の地図にする Python が、トークンが少なくて済んだ（絵 1 枚 約 7,700〜15,000 トークン）。黒いふちどりで形を区切り、主役を 1 つ大きく描くと分かりやすい。
- **GitHub Pages の配信が失敗することがある**（2026-11-09、v72）：master の push のあと「pages build and deployment」の deploy が GitHub 側のエラー（500・syncing_files の時間切れ）で失敗し、サイトは前の版のままになった。失敗した配信の流し直し（re-run）は Queued のまま進まず、キャンセルもできなかった。新しいコミットを master に push すると新しい配信が始まる。公開のあとは actions の一覧（mcp__github__actions_list）で配信の成功を確かめてから、ユーザーに実機の確認を頼む。
- **長い会話では PM の返事 1 回ごとの消費が大きい**。大きな作業は新しい会話で始める。

## 5. 決めごとの要点（詳しくは CLAUDE.md）

- 公開はユーザーの「公開して」のあとだけ。版は `common/version.js` の version・date と `sw.js` の `CACHE_VERSION` を一緒に（日付は公開する日）。
- 関門：Chromium の smoke と full、WebKit の smoke（`HEADED=1 BROWSER=webkit WORKERS=1 xvfb-run -a`）。変異テストは仕組みを変えたときだけ、そのゲームの関わる分を ONLY と M で絞って流す。
- 進め方：Opus が計画 → Sonnet・Haiku が小さなタスク → Opus が確かめる → レビュー（新しいゲームは 6 観点、直しは技術＋UX）→ 指摘を直してコミット → 版上げ・関門 → 公開。
- 公開は fast-forward の push（`git push origin <作業ブランチ>:master`）。force push・履歴の書き換えはしない。PR はユーザーが頼んだときだけ。
- 答え方：日本語・初級者向け・おすすめ 1 つ・「事実に基づいて回答します」「以下は私の推測です」の前置き・改善は 4 段（直接・根本・直近・中長期）。
