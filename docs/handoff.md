## 7. この会話で学んだこと（進め方）

- 仕様を変えるときは、**約束の文書に章を足してから**担当に渡す（ミチビキ空港 §19、いろびん §17.7〜17.9、まとめてポン §8〜§10）。ユーザーの言葉をそのまま引用する。
- 同じファイルを2人の担当に同時に触らせない。後からの決定は SendMessage で作業中の担当に伝える。
- レビューは**作った直後に1回**、技術・UX・中毒性と品質を**同時に**流す。直しは「約束に章を足す → Opus（ロジック・不具合）→ Sonnet（遊びやすさ）」の順にし、同じファイルを同時に触らせない。
- テスト担当が関門を流している間に直しが要るときは、別の worktree（`feature/<名前>-fix`）で直して merge する（関門を流している worktree のファイルを変えない）。
- 難しさは**人らしい自動プレイ**で判断する：上手な bot と、速い（fast）・ふつう（avg）・ゆっくり（slow）の打ち手を Node で回し、結果の数（着陸数・時間など）を比べる（ミチビキ空港の B4・C1 はこれで決めた）。台本は scratchpad に置いたので消えている可能性がある。必要なら考え方から作り直す。
- 公開は「関門合格 → ユーザーに結果を見せて承認 →（Haiku が）fast-forward の push → PM が origin/master と版を確かめる」。v22〜v24 ともこの順で問題なし。
- 公開済みの master を作業ブランチに取り込むと、tests/README.md・tests/design.md・tests/mutants/mutate.mjs・common/sfx.js・docs/game-plan.md の追記どうしがぶつかる。両方の追記を残せばよい。
- この会話も長くなった。大きな作業ごとに新しい会話にする。
- （v25 で追加）遊ぶ時間の目安は、**平均だけでなく最大の間隔**も測る（もくもくこうばで約70分の空白を、平均が見逃した）。
- 組み合わせ担当を1人置くと、並列で作った部品の食い違い（予備の古い値・推測した名前）を早く直せる。
- ユーザーの追加の要望は、作業中の担当へ SendMessage で足すと、同じブランチで続けて作れる。
- （v26 で追加）実機の画面録画は「そう見えてしまう」問題を見つけるのに役立つ（なえぎの件は、画面と計算の切り捨ての食い違いだった）。
- サブエージェントが自分で予約のお知らせ（1回だけ）を作ることがある。
- 並列の関門で負荷による不安定が出たら、単独で流し直して分け、ユーザーに伝えて判断してもらう。
- （v27 で追加）自動プレイで目安どうしの食い違い（1回の長さ×星の数と合計時間）が見つかったら、数値を無理に合わせず、すぐユーザーに選んでもらう（今回は「1つの星を長くする」）。
- （v27 で追加）1つの区切りが長いゲームは、レビューの前に「最初の30秒で何が起きるか」を測る（ほしくだきは最初の60秒で9%しか欠けず、退屈の原因だった）。
- （v27 で追加）担当の申し送り（DOM・API・注意点）は scratchpad の1つのファイルに足していき、次の担当の指示で読ませると食い違いが減る。
