# あまいものあつめ：絵を 100 枚ほど足す計画（著作権の心配がない元絵から作る）

- 作成：2026-10-27（PM・Opus）。状態：**計画（レビュー前）**。作り始めるのはユーザーの承認のあと。
- ユーザーの言葉（そのまま）：「絵をもっと増やすべきです。手軽に増やすことができるよう、著作権フリーのいらすとや写真、絵画などをもとに絵を作成するエージェントを起動し、あと100枚ほど追加してください。データのサイズが気になります。まずは計画を立案してください。計画はデビューをするようにしてください。まずはこれを先に進めてください。」（「デビュー」は音声入力の誤りで「レビュー」の意味と受け取った）
- 前提：約束の文書 [docs/ari-contract.md](../ari-contract.md)（48 枚・文字の地図・§2.6 の絵の決まり 1〜8・§2.7 の 49 枚目から先の出し方）。ゲーム本体はまだ作っていない。

---

## 1. 目的と、できあがりの形

- 約束の 48 枚に、**約 100 枚（49〜148 枚目）を足す**。足した絵は §2.7 のとおり「くり返しより先」に出る。
- 1 枚は今と同じ**文字の地図**（`.` と 10 色の文字。最大 32×24）。ゲームの仕組みは変えない。
- 元にした絵（写真・絵画など）の出どころと権利を、1 枚ずつ記録する（§3）。
- 絵を作る手順を**道具（台本）にして残す**。次に足すときも、元絵を選ぶ → 台本で変換 → 手で整える、で増やせるようにする（「手軽に増やす」）。

## 2. データの大きさ（ユーザーの心配）

事実（約束の形から計算）：

| 項目 | 1 枚 | 100 枚 |
|---|---|---|
| 文字の地図（最大 32×24＝768 字＋改行・引用符） | 最大 約 0.9 KB、平均 約 0.5 KB | 約 50〜90 KB |
| 名前・id・季節などの付け足し | 約 0.05 KB | 約 5 KB |
| **合計（ファイルのまま）** | | **約 55〜95 KB** |
| 送るときの大きさ（GitHub Pages は gzip で縮めて送る。事実：28×22 の でたらめな絵 100 枚〔70 KB〕を gzip すると 20 KB。本物の絵は同じ色が続くので、以下は私の推測で もっと小さい） | | **約 10〜20 KB** |

- 比べると（事実）：いまのいろびんの `render.js` 1 本が約 100 KB、いろびんの js 全部で約 350 KB。フォントはこれより大きい。**100 枚足しても、ゲーム全体の読み込みは数 % しか増えない**。
- 元の写真・絵画のファイルは**リポジトリに入れない**（作業場所 scratchpad だけに置き、作り終えたら消す）。入れるのは文字の地図だけ。
- それでも小さくしたいときの手（今回は使わない。300 枚を超えたら考える）：ランレングス（「R が 12 個」を `12R` と書く）で 1/3 に。または、遊ぶ面の絵だけ後から読む。

## 3. 元絵の権利（いちばん大事）

### 3.1 使ってよい元絵（おすすめ）
- **パブリックドメイン（作者の死後 70 年を過ぎた絵画など）と、CC0（権利を放棄した写真・絵）だけ**を元にする。出どころの例：ウィキメディア・コモンズ（PD・CC0 と表示のもの）、メトロポリタン美術館のオープンアクセス（CC0）、米国ナショナル・ギャラリーのオープンアクセス（CC0）、シカゴ美術館（CC0 の作品）。
- 1 枚ずつ、**元絵の URL・題名・作者・権利の表示（PD か CC0）・取った日**を `docs/amai-credits.md` に書く。ゲームの遊び方の画面かずかんの奥に「えの もとに した さくひん」の一覧を出す（CC0 では義務ではないが、出どころを示しておく）。

### 3.2 使わない元絵（理由つき）
- **いらすとや**：以下は私の推測を含むので、ユーザーが規約を確かめること。いらすとやは無料で使えるが「著作権フリー」ではなく、作者が著作権を持ち、利用規約に条件がある（商用で 1 つの作品に使える数の上限など）。ドット絵に変えても元の絵と分かる形が残るので「元の絵を加工したもの」になり、規約の範囲か判断が要る。**そのため今回は使わない**（ユーザーが規約を読んで「使ってよい」と決めたときだけ、別に考える）。
- 「フリー素材」と書いてあるだけで権利の表示がはっきりしない絵、CC BY（名前の表示が義務）・CC BY-SA（同じ条件で公開する義務）の絵、商標・キャラクター（アニメ・ゲーム・会社のマスコットなど）が写った写真、人の顔がはっきり写った写真。
- 他社のゲームの絵（参考の録画のゲームも含む）。

### 3.3 ドット絵にしたあとの確かめ
- 32×24 以下に小さくすると、元の絵とはほとんど別の絵になる（以下は私の推測）。それでも、上の 3.1 の元絵だけを使う。
- 1 枚ずつ「何の絵か分かるか」を PM が見本の一覧（§5 の見本の一枚絵）で確かめる。

## 4. 今の作業環境でできること・できないこと（事実）

- **この作業環境は、ウィキメディア・コモンズ・美術館の API などへの通信を許していない**（2026-10-27 に試して、どれも 403 で断られた）。そのため、エージェントが自分で元絵を探して取ってくることは、**今のままではできない**。
- 道は 3 つ（**おすすめは A**）：
  - **A（おすすめ）**：環境の設定で、決まった数か所だけ通信を許す（ネットワークの「許可するドメイン」に `commons.wikimedia.org`・`upload.wikimedia.org`・`collectionapi.metmuseum.org`・`images.metmuseum.org` などを足す）。エージェントが CC0・PD の元絵を探し、権利の表示を API で確かめて取ってくる。
  - **B**：ユーザーが元絵（自分で撮った写真、または PD・CC0 と確かめた絵）を会話にアップロードする。エージェントはそれを変換する。手間はユーザー側にかかる。
  - **C**：元絵を使わず、エージェントが題材の名前から文字の地図を手で描く（約束の 48 枚と同じ作り方）。権利の心配はいちばん少ないが、「写真・絵画をもとに」というユーザーの案とは違う。
- 道 A と B は、変換の台本（§5）は同じものを使う。

## 5. 作り方（手順と道具）

1. **題材の一覧を先に決める**（PM・Opus）：約 100 個。約束の 48 枚と重ならない、子どもに分かる身近なもの（どうぶつ・むし・くだもの・やさい・たべもの・のりもの・どうぐ・しぜん・たてもの・季節）。各題材に「段（XL・XXL など）・使う色の案・季節」を付ける。一覧はユーザーに見せて承認をもらう。
2. **元絵を選ぶ**（道 A：エージェント。道 B：ユーザー）：1 題材に 1 枚。背景が単純で、形がはっきりした絵・写真を選ぶ。権利を §3.1 で確かめ、`docs/amai-credits.md` の下書きに書く。
3. **変換の台本**（`tools/amai-pixel.py`。Python と画像の道具 Pillow。作業環境にある）：
   - 元絵から題材の所を切り出す → 背景を抜く（四隅の色に近い所を空きに）→ 段の大きさ（例 28×22）に縮める → **約束の 10 色に色を合わせる**（いちばん近い色。使う色の案の中だけに絞る）→ 1〜2 個だけの色を周りの色に寄せる（決まり 4）→ 閉じた空きを埋める（決まり 5）→ むだな空きの行・列を削る（決まり 1）→ 文字の地図を書き出す。
   - 台本はリポジトリに入れてよい（小さい。元絵は入れない）。`tests/` ではなく `tools/` に置き、ゲームの配信物（`APP_FILES`）には入れない。
4. **手で整える**（エージェント・Sonnet）：台本の出力は線がぎざぎざになりやすいので、目・口・ふちどり（決まり 8）を手で直す。直したら §2.6 の決まり 1〜8 を Node の確かめ（テスト AL2 と同じ中身）で通す。
5. **見本の一枚絵で確かめる**（PM・Opus、そのあとユーザー）：10 枚ずつ、元絵の縮小とドット絵を並べた画像を作り、「何の絵か分かるか」「約束の 48 枚と見た目の感じがそろっているか」を見る。だめな絵は 4 に戻すか、題材を変える。
6. **ファイルに入れる**：`games/amai/pictures-c.js`（49〜98 枚目）と `pictures-d.js`（99〜148 枚目）に分けて書く（1 ファイルを大きくしすぎない。担当が並列に書ける）。`PICTURE_ORDER` の最後に足す。`index.html` の読み込みと `sw.js` の `APP_FILES` に足す（約束 §2.6「絵を足すとき」）。
7. **面として遊べるか**：ロジック担当の生成（約束 §2）で、足した 100 枚が全部「必ず解ける面」になり、生成の時間が上限の中に入るかを Node で確かめる。

## 6. 担当とモデル（CLAUDE.md 3 章）

| 仕事 | 担当 | 理由 |
|---|---|---|
| 題材の一覧・段と色の割り当て | Opus（PM） | 全体の釣り合いを決める判断 |
| 変換の台本を作る | Opus | 作りながら判断が要る（色の合わせ方・閉じた空きの埋め方） |
| 元絵を探して権利を確かめる（道 A） | Sonnet × 2（50 枚ずつ） | 決まった手順（§3.1 の条件で探して記録） |
| 台本を流して手で整える | Sonnet × 2（50 枚ずつ、ファイル c・d を分ける） | 決まりに沿って直す作業 |
| 見本の一枚絵で確かめる | Opus（PM）→ ユーザー | 品質の判断 |
| 版上げ・関門・公開 | Haiku | 決まった手順 |

- 10 枚ごとに PM が確かめる（だめな絵がたまらないように）。

## 7. いつ入れるか（順番）

- ゲーム本体（約束の 48 枚）は**まだ作っていない**。おすすめの順番：
  1. **先に本体を作って公開**（48 枚。約束どおり）。
  2. そのあとで、この計画で 100 枚を足す（ゲームを遊んで、絵の大きさや色の決まりが正しいと分かってから足すほうが、作り直しが少ない）。
- ただし題材の一覧づくり（§5 の 1）と変換の台本（§5 の 3）は、本体と並べて先に進めてよい（本体のファイルに触らないため）。

## 8. 危ないこと（リスク）と対策

| 危ないこと | 対策 |
|---|---|
| 権利の表示が間違っている元絵を使ってしまう | §3.1 の出どころだけにする。API の権利の欄（例：美術館の `isPublicDomain`）を記録に残す。PM が 10 枚ごとに確かめる |
| 32×24 では何の絵か分からない | 題材を「形がはっきりしたもの」にする。見本の一枚絵で確かめ、だめなら題材を変える |
| 約束の 48 枚と見た目の感じがそろわない | 決まり 8（ふちどり・背景は塗らない）を台本と手直しで守る。見本の一枚絵で並べて比べる |
| 生成が重くなる・解けない面になる | §5 の 7 で 100 枚全部を Node で確かめる |
| 通信が許されず元絵が取れない | 道 B か C に切り替える（§4） |
| データが大きくなる | §2 の見積もり（送るのは約 10〜20 KB）。300 枚を超えたら圧縮を考える |

## 9. ユーザーに決めてもらうこと（このあと）

1. 元絵の取り方：A（通信を許す。おすすめ）／B（ユーザーがアップロード）／C（元絵なしで描く）。
2. いらすとやを使わないこと（§3.2）でよいか。
3. 入れる順番：本体を先に公開してから 100 枚を足す（おすすめ）でよいか。
